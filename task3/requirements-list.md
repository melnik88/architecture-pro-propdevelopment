# Список требований к внешним интеграциям "Умный дом"

## 1. Требования к безопасности

### 1.1. Аутентификация и идентификация

| № | Требование | Приоритет | Обоснование |
|---|------------|-----------|-------------|
| 1 | Система ДОЛЖНА использовать OAuth 2.0 с Authorization Code Flow + PKCE для аутентификации пользователей мобильного приложения | Критический | Защита от перехвата кода авторизации, соответствие современным стандартам безопасности |
| 2 | Система ДОЛЖНА использовать Mutual TLS (mTLS) для взаимной аутентификации между Smart Home Integration Service и внешней платформой | Критический | Гарантия подлинности обеих сторон при межсервисном взаимодействии |
| 3 | Система ДОЛЖНА использовать JWT токены с подписью RS256 (RSA + SHA-256) | Критический | Невозможность подделки токенов, криптографическая стойкость |
| 4 | Access токены ДОЛЖНЫ иметь время жизни не более 15 минут | Высокий | Минимизация окна возможной компрометации токена |
| 5 | Refresh токены ДОЛЖНЫ иметь время жизни не более 30 дней | Высокий | Баланс между безопасностью и удобством пользователя |
| 6 | Система ДОЛЖНА выполнять автоматическую ротацию клиентских сертификатов каждые 90 дней | Высокий | Снижение риска компрометации долгоживущих сертификатов |

### 1.2. Авторизация и управление доступом

| № | Требование | Приоритет | Обоснование |
|---|------------|-----------|-------------|
| 1 | Система ДОЛЖНА реализовать RBAC (Role-Based Access Control) с ролями: Собственник, Гость, Администратор ЖК | Критический | Чёткое разграничение прав доступа по ролям |
| 2 | Система ДОЛЖНА реализовать ABAC (Attribute-Based Access Control) для проверки временных рамок и конкретных устройств | Высокий | Гибкое управление доступом на основе контекста |
| 3 | Система ДОЛЖНА проверять права доступа при каждом запросе к устройствам "Умного дома" | Критический | Предотвращение несанкционированного доступа |
| 4 | Система ДОЛЖНА поддерживать временные доступы с автоматической деактивацией по истечении срока | Высокий | Безопасное предоставление доступа гостям |
| 5 | Система ДОЛЖНА логировать все операции с правами доступа (создание, изменение, удаление) | Высокий | Аудит изменений прав доступа |

### 1.3. Шифрование данных

| № | Требование | Приоритет | Обоснование |
|---|------------|-----------|-------------|
| 1 | Система ДОЛЖНА использовать TLS 1.3 для всех соединений | Критический | Современный стандарт защиты данных при передаче |
| 2 | Система НЕ ДОЛЖНА поддерживать устаревшие протоколы TLS 1.0 и TLS 1.1 | Критический | Защита от известных уязвимостей старых протоколов |
| 3 | Система ДОЛЖНА использовать Perfect Forward Secrecy (PFS) | Высокий | Защита прошлых сессий при компрометации ключей |
| 4 | Биометрические данные ДОЛЖНЫ храниться только на стороне внешней платформы | Критический | Минимизация рисков утечки биометрии |
| 5 | Биометрические данные ДОЛЖНЫ передаваться только в зашифрованном виде | Критический | Защита чувствительных данных при передаче |
| 6 | Система ДОЛЖНА использовать AES-256 для шифрования чувствительных данных в БД | Высокий | Защита данных в состоянии покоя |
| 7 | Видеопоток с домофона ДОЛЖЕН использовать end-to-end шифрование | Критический | Конфиденциальность видеоданных |
| 8 | Система ДОЛЖНА использовать SRTP (Secure Real-time Transport Protocol) для видеопотока | Высокий | Защита видео в реальном времени |

### 1.4. Защита персональных данных

| № | Требование | Приоритет | Обоснование |
|---|------------|-----------|-------------|
| 1 | Система ДОЛЖНА передавать только минимально необходимые данные для работы сервиса | Критический | Принцип минимизации данных (ФЗ-152) |
| 2 | Биометрические данные НЕ ДОЛЖНЫ храниться в системах PropDevelopment | Критический | Снижение рисков и соответствие законодательству |
| 3 | Система ДОЛЖНА маскировать персональные данные в логах | Высокий | Защита ПДн при логировании |
| 4 | Логи ДОЛЖНЫ храниться не более 90 дней | Средний | Баланс между аудитом и минимизацией хранения |
| 5 | Система ДОЛЖНА получать явное согласие пользователя на обработку биометрических данных | Критический | Соответствие ФЗ-152 ст. 11 |
| 6 | Система ДОЛЖНА предоставлять пользователю возможность удаления своих данных | Высокий | Право на забвение (GDPR-подобные требования) |
| 7 | Система ДОЛЖНА соответствовать требованиям ФЗ-152 "О персональных данных" | Критический | Законодательное требование РФ |

### 1.5. Защита API

| № | Требование | Приоритет | Обоснование |
|---|------------|-----------|-------------|
| 1 | Система ДОЛЖНА ограничивать количество запросов до 100 запросов/минуту на пользователя | Высокий | Защита от злоупотреблений и DDoS |
| 2 | Система ДОЛЖНА ограничивать критические операции (открытие двери) до 10 запросов/минуту | Критический | Предотвращение атак на физическую безопасность |
| 3 | Система ДОЛЖНА валидировать все входные данные | Критический | Защита от инъекций и некорректных данных |
| 4 | Система ДОЛЖНА защищать от SQL-инъекций, XSS, CSRF | Критический | Защита от распространённых веб-атак |
| 5 | Система ДОЛЖНА санитизировать данные перед передачей во внешнюю систему | Высокий | Предотвращение передачи вредоносных данных |
| 6 | Система ДОЛЖНА использовать заголовки безопасности: Content-Security-Policy, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Strict-Transport-Security | Высокий | Защита от различных типов атак на уровне HTTP |

### 1.6. Мониторинг и аудит безопасности

| № | Требование | Приоритет | Обоснование |
|---|------------|-----------|-------------|

| 2 | Система ДОЛЖНА логировать все операции с правами доступа | Критический | Отслеживание изменений безопасности |

| 5 | Система ДОЛЖНА отправлять алерты при превышении порогов запросов | Высокий | Оперативное реагирование на аномалии |
| 6 | Система ДОЛЖНА мониторить время отклика внешней системы | Средний | Контроль доступности сервиса |
| 7 | Система ДОЛЖНА проводить регулярный аудит прав доступа (ежемесячно) | Средний | Выявление избыточных прав |

## 2. Протоколы аутентификации и авторизации

### 2.1. OAuth 2.0

| № | Требование | Описание |
|---|------------|----------|
| 1 | Использование Authorization Code Flow + PKCE | Для аутентификации мобильного приложения с защитой от перехвата кода |
| 2 | Поддержка Refresh Tokens | Для обновления доступа без повторной аутентификации пользователя |
| 3 | Scope-based авторизация | Разграничение прав доступа через OAuth scopes: `smart_home:read`, `smart_home:write`, `smart_home:admin` |
| 4 | Отзыв токенов | Возможность отзыва access и refresh токенов при компрометации |

### 2.2. Mutual TLS (mTLS)

| № | Требование | Описание |
|---|------------|----------|
| 5 | Использование клиентских сертификатов | Для взаимной аутентификации между Smart Home Integration Service и внешней платформой |
| 6 | Проверка цепочки сертификатов | Валидация сертификатов до доверенного корневого CA |
| 7 | Ротация сертификатов | Автоматическая ротация каждые 90 дней |
| 8 | Отзыв сертификатов | Поддержка OCSP (Online Certificate Status Protocol) для проверки статуса сертификатов |

### 2.3. JWT (JSON Web Tokens)

| № | Требование | Описание |
|---|------------|----------|
| 9 | Подпись RS256 | Использование RSA + SHA-256 для подписи токенов |
| 10 | Структура токена | Включение claims: `sub` (user_id), `iat` (issued at), `exp` (expiration), `scope` (права доступа) |
| 11 | Время жизни access token | Не более 15 минут |
| 12 | Время жизни refresh token | Не более 30 дней |
| 13 | Валидация токенов | Проверка подписи, срока действия, issuer, audience при каждом запросе |

### 2.4. RBAC (Role-Based Access Control)

| № | Роль | Права доступа |
|---|------|---------------|
| 14 | Собственник | Полный доступ к своим устройствам: открытие, просмотр видео, управление правами гостей, просмотр истории |
| 15 | Гость | Ограниченный доступ: открытие двери по временному коду/QR в разрешённое время |
| 16 | Администратор ЖК | Управление устройствами всего ЖК, просмотр общей статистики, управление правами собственников |

### 2.5. ABAC (Attribute-Based Access Control)

| № | Атрибут | Описание |
|---|---------|----------|
| 17 | Временные рамки | Проверка времени доступа (например, гость может войти только с 10:00 до 18:00) |
| 18 | Конкретные устройства | Ограничение доступа к определённым домофонам/шлагбаумам |
| 19 | Геолокация | Проверка местоположения пользователя (опционально) |
| 20 | Тип устройства | Разные права для мобильного приложения и веб-интерфейса |

### 2.6. Webhook Security

| № | Требование | Описание |
|---|------------|----------|
| 21 | HMAC-SHA256 подпись | Каждый webhook подписывается секретным ключом |
| 22 | Timestamp validation | Отклонение запросов старше 5 минут |
| 23 | Nonce | Использование уникального идентификатора для предотвращения replay-атак |
| 24 | IP Whitelisting | Приём webhooks только с известных IP-адресов платформы |

## 3. Организация взаимодействия между системами

### 3.1. Архитектурные компоненты

| № | Компонент | Назначение | Технологии |
|---|-----------|------------|------------|
| 1 | API Gateway | Единая точка входа, маршрутизация, аутентификация, rate limiting, логирование | Kong / AWS API Gateway |
| 2 | Smart Home Integration Service | Адаптер к внешнему API, управление правами, кэширование, обработка событий | Node.js / Kotlin + Spring Boot |
| 3 | smart-home-db | Хранение прав доступа, истории событий, временных доступов | PostgreSQL |
| 4 | Мобильное приложение | Интерфейс для собственников: управление доступом, просмотр видео, открытие устройств | iOS / Android |

### 3.2. Сценарии взаимодействия

#### Сценарий 1: Открытие домофона собственником

| Шаг | Участник | Действие |
|-----|----------|----------|
| 1 | Пользователь | Нажимает кнопку "Открыть дверь" в приложении |
| 2 | Мобильное приложение | Отправляет `POST /api/v1/smart-home/intercom/open` с JWT токеном |
| 3 | API Gateway | Проверяет JWT, rate limit, логирует, перенаправляет на Smart Home Integration Service |
| 4 | Smart Home Integration Service | Проверяет права доступа, формирует запрос к внешней платформе с mTLS |
| 5 | Платформа "Умный дом" | Проверяет сертификат, токен, отправляет команду на устройство, возвращает результат |
| 6 | Smart Home Integration Service | Логирует результат, возвращает ответ через API Gateway |
| 7 | Мобильное приложение | Показывает уведомление "Дверь открыта" |

#### Сценарий 2: Автоматическое открытие по биометрии

| Шаг | Участник | Действие |
|-----|----------|----------|
| 1 | Домофон | Распознаёт лицо пользователя |
| 2 | Платформа "Умный дом" | Обрабатывает биометрию, определяет user_id |
| 3 | Платформа "Умный дом" | Отправляет webhook `POST /api/v1/webhooks/smart-home/access-request` с HMAC подписью |
| 4 | Smart Home Integration Service | Проверяет подпись, timestamp, nonce; проверяет права доступа и временные ограничения |
| 5 | Smart Home Integration Service | Возвращает решение: `{ "access": "granted" }` или `{ "access": "denied" }` |
| 6 | Платформа "Умный дом" | Открывает/не открывает дверь, логирует событие |
| 7 | Smart Home Integration Service | Отправляет push-уведомление собственнику: "Дверь открыта по биометрии в 14:30" |

#### Сценарий 3: Предоставление временного доступа гостю

| Шаг | Участник | Действие |
|-----|----------|----------|
| 1 | Собственник | Создаёт временный доступ: `POST /api/v1/smart-home/access/temporary` |
| 2 | Smart Home Integration Service | Создаёт запись в БД, генерирует PIN/QR-код, отправляет данные на платформу |
| 3 | Smart Home Integration Service | Отправляет SMS/push гостю с инструкциями |
| 4 | Гость | Вводит PIN на домофоне или показывает QR-код |
| 5 | Платформа "Умный дом" | Проверяет валидность, отправляет webhook в PropDevelopment для логирования |
| 6 | Smart Home Integration Service | Логирует событие, отправляет уведомление собственнику |
| 7 | Платформа "Умный дом" | Открывает дверь |
