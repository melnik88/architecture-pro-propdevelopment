# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

### 1. Доступ к секретам

**Кто:** `system:serviceaccount:secure-ops:monitoring`

**Где:** namespace `kube-system`, секрет `default-token-abc123`

**Почему подозрительно:**
- ServiceAccount из namespace `secure-ops` пытается получить доступ к секретам в критическом namespace `kube-system`
- Доступ к токенам по умолчанию может быть использован для эскалации привилегий
- ServiceAccount `monitoring` не должен иметь доступа к секретам других namespace
- Попытка доступа к `etcd-certs` особенно опасна, так как это критические сертификаты кластера

**Статус:** Частично заблокировано (403 Forbidden на некоторые секреты)

**Рекомендации:**
- Проверить, кто создал ServiceAccount `monitoring` и с какой целью
- Убедиться, что у ServiceAccount нет избыточных прав через RoleBinding/ClusterRoleBinding
- Ограничить доступ к namespace `kube-system` только для системных компонентов

---

### 2. Привилегированные поды

**Кто:** `kubernetes-admin`

**Где:** namespace `secure-ops`, под `privileged-pod`

**Комментарий:**
- Создан под с флагом `privileged: true`, что даёт контейнеру полный доступ к хост-системе
- Привилегированный режим позволяет:
  - Обходить все ограничения безопасности
  - Получать доступ к устройствам хоста
  - Монтировать файловые системы хоста
  - Выполнять операции на уровне ядра
- Использование образа `alpine` с командой `sleep 3600` указывает на возможную подготовку к атаке
- Легитимные причины для привилегированных подов крайне редки (например, системные DaemonSet)

**Уровень угрозы:** Критический

**Рекомендации:**
- Немедленно удалить под `privileged-pod`
- Внедрить PodSecurityPolicy/PodSecurityStandards для запрета привилегированных подов
- Расследовать, кто и зачем создал этот под
- Проверить, не были ли выполнены какие-либо действия из этого пода

---

### 3. Использование kubectl exec в чужом поде

**Кто:** `kubernetes-admin`

**Где:** namespace `kube-system`, под `coredns-5d78c9869d-abc12`

**Что делал:** Выполнение команды `cat /etc/resolv.conf`

**Почему подозрительно:**
- Выполнение команд в системных подах namespace `kube-system` может быть использовано для:
  - Сбора информации о конфигурации кластера
  - Получения доступа к секретам, смонтированным в под
  - Модификации конфигурации критических компонентов
- CoreDNS - критический компонент кластера, отвечающий за DNS
- Хотя команда `cat /etc/resolv.conf` выглядит безобидно, это может быть разведкой перед более серьёзной атакой
- Легитимные администраторы обычно используют логи и метрики вместо прямого exec

**Статус:** Выполнено успешно (код 101 - Switching Protocols для WebSocket)

**Рекомендации:**
- Ограничить возможность exec в системные поды через RBAC
- Использовать аудит для отслеживания всех exec-операций
- Проверить, не были ли выполнены другие команды в этом или других системных подах
- Рассмотреть использование admission webhooks для блокировки exec в критические поды

---

### 4. Создание RoleBinding с правами cluster-admin

**Кто:** `kubernetes-admin`

**Где:** namespace `secure-ops`, RoleBinding `escalate-binding`

**К чему привело:**
- ServiceAccount `monitoring` получил права `cluster-admin` через RoleBinding
- Это критическая эскалация привилегий - `cluster-admin` имеет полный контроль над кластером
- ServiceAccount теперь может:
  - Создавать, изменять и удалять любые ресурсы в любых namespace
  - Читать все секреты, включая токены и сертификаты
  - Изменять RBAC-политики
  - Удалять критические компоненты кластера
  - Создавать привилегированные поды
- Это нарушает принцип наименьших привилегий

**Уровень угрозы:** Критический - полная компрометация кластера

**Рекомендации:**
- **НЕМЕДЛЕННО** удалить RoleBinding `escalate-binding`
- Отозвать все токены ServiceAccount `monitoring`
- Провести полный аудит всех действий, выполненных от имени этого ServiceAccount
- Внедрить admission controller для предотвращения создания RoleBinding с cluster-admin
- Ограничить, кто может создавать RoleBinding/ClusterRoleBinding
- Рассмотреть использование OPA/Gatekeeper для политик безопасности

---

### 5. Удаление audit-policy.yaml

**Кто:** пользователь `admin`

**Где:** попытка удаления `/api/v1/namespaces/kube-system/configmaps/audit-policy`

**Возможные последствия:**
- Удаление audit-policy отключит аудит событий в кластере
- Без аудита невозможно отследить:
  - Несанкционированный доступ
  - Изменения в конфигурации
  - Создание/удаление ресурсов
  - Эскалацию привилегий
- Это классическая тактика атакующих - "замести следы"
- Отключение аудита позволяет проводить атаки незаметно

**Статус:** Заблокировано (403 Forbidden)

**Почему заблокировано:**
- У пользователя `admin` нет прав на удаление ConfigMap в namespace `kube-system`
- Это правильная настройка RBAC - даже администраторы не должны иметь возможность отключать аудит

**Рекомендации:**
- Расследовать, кто такой пользователь `admin` и почему он пытался удалить audit-policy
- Убедиться, что audit-policy хранится в защищённом месте и не может быть изменён
- Рассмотреть использование immutable ConfigMap для audit-policy
- Настроить алерты на попытки изменения или удаления audit-policy
- Экспортировать логи аудита во внешнюю систему (SIEM) для защиты от удаления

Это указывает на то, что:
- Политики RBAC работают корректно и блокируют несанкционированный доступ
- Атакующий пытается найти слабые места в системе безопасности
- Необходимо усилить мониторинг попыток неавторизованного доступа

## Ошибки в политике RBAC

### 1. Избыточные права для kubernetes-admin
- Пользователь `kubernetes-admin` имеет возможность создавать привилегированные поды
- Может создавать RoleBinding с cluster-admin
- Может выполнять exec в системных подах

**Рекомендация:** Даже для администраторов следует ограничить возможность создания привилегированных подов и RoleBinding с высокими привилегиями

### 2. Отсутствие ограничений на создание ServiceAccount
- Любой пользователь с правами на создание ServiceAccount может создать его и затем попытаться дать ему права

**Рекомендация:** Ограничить создание ServiceAccount и автоматическое монтирование токенов

### 3. Недостаточная сегрегация namespace
- ServiceAccount из `secure-ops` пытается получить доступ к `kube-system`
- Необходимо усилить изоляцию между namespace

**Рекомендация:** Использовать NetworkPolicy и более строгие RBAC-политики для изоляции namespace

### 4. Отсутствие PodSecurityPolicy/PodSecurityStandards
- Нет механизма предотвращения создания привилегированных подов на уровне admission control

**Рекомендация:** Внедрить PodSecurityStandards (restricted) для всех namespace кроме системных

## Вывод

Анализ audit.log выявил **серьёзную попытку компрометации кластера Kubernetes**. Обнаружена организованная цепочка атаки, включающая:

- ✅ Попытки несанкционированного доступа к секретам (частично заблокировано)
- ❌ Создание привилегированного пода (успешно)
- ❌ Выполнение команд в системных подах (успешно)
- ✅ Попытка отключения аудита (заблокировано)
- ❌ Критическая эскалация привилегий через RoleBinding (успешно)

### Критические проблемы:
1. **ServiceAccount `monitoring` получил права cluster-admin** - полная компрометация кластера
2. **Создан привилегированный под** - возможен доступ к хост-системе
3. **Выполнены команды в системных подах** - возможна утечка конфигурации

### Немедленные действия:
1. Удалить RoleBinding `escalate-binding`
2. Удалить под `privileged-pod`
3. Отозвать токены ServiceAccount `monitoring`
4. Провести полный аудит всех действий за период атаки
5. Проверить целостность системных компонентов

### Долгосрочные меры:
1. Внедрить PodSecurityStandards
2. Усилить RBAC-политики
3. Настроить алерты на подозрительные события
4. Внедрить admission webhooks для дополнительного контроля
5. Экспортировать логи во внешнюю SIEM-систему
6. Провести обучение команды по безопасности Kubernetes
